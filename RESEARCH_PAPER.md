# Publication-ready manuscript for ICCISCS 2026

## A. Project understanding

This project is a React 19/Vite dashboard backed by a Flask API and a Python churn-prediction pipeline. The dataset is generated by `backend/main.py`, rather than loaded from an external provider: 1,000 simulated customers are observed for six monthly records each (6,000 rows). Customer-level aggregation produces 1,000 modeling records. The pipeline adds behavioural, customer-lifetime-value (CLV), and sentiment features; the sentiment component fell back to a neutral score of 0.5 in the reproducible run because the transformer model could not load. A `ColumnTransformer` median-imputes numeric values, most-frequent-imputes categorical values, standardizes numeric variables, and one-hot encodes categorical variables. Logistic Regression, Random Forest, and XGBoost are evaluated with a stratified 80:20 split, `random_state=42`. The best ROC–AUC in the verified run was Logistic Regression (0.8329). The dashboard submits an individual prediction and displays retention advice based on risk bands and a CLV heuristic.

## Abstract

Customer churn prediction can help a telecommunications provider prioritize retention activity before a customer terminates service. This paper reports the implemented behaviour of a reproducible churn-prediction application comprising a Python machine-learning pipeline, a Flask application programming interface (API), and a React dashboard. Unlike studies based on operator data, the current implementation generates a controlled synthetic panel of 1,000 customers with six monthly observations per customer (6,000 rows). It aggregates the panel to one record per customer, derives service-usage, complaint, recharge, customer-lifetime-value (CLV), and behavioural-change variables, and evaluates Logistic Regression, Random Forest, and XGBoost classifiers. Numeric variables are median-imputed and standardized; categorical variables are most-frequent-imputed and one-hot encoded. In a stratified 80:20 hold-out evaluation with random state 42, Logistic Regression achieved the highest ROC–AUC (0.8329), with accuracy 0.7900, precision 0.7593, recall 0.5857, and F1-score 0.6613. Random Forest achieved a slightly higher precision (0.7647), whereas XGBoost achieved the highest recall (0.6143), but neither exceeded the selected model in ROC–AUC. The dashboard exposes individual risk predictions and rule-based retention recommendations using predicted risk and CLV. The results demonstrate an auditable prototype, while its synthetic label-generation mechanism, preprocessing-before-splitting sequence, and lack of a real external validation set limit operational interpretation.

## Keywords

Telecommunications; customer churn prediction; synthetic data; Logistic Regression; explainable artificial intelligence; SHAP; retention recommendation.

## I. Introduction

Customer attrition reduces the recurring-revenue base of subscription businesses and motivates early identification of customers likely to discontinue service. Churn prediction frames this task as supervised binary classification: customer attributes and recent behaviour are used to estimate the probability of a churn event. In an intervention setting, an estimate is useful only when it can be translated into a ranked work list and a defensible action. Prior churn work therefore emphasizes both predictive accuracy and the economic consequences of whom a campaign targets [1].

The present project was built as an end-to-end demonstration rather than as an analysis of an operator-owned dataset. It intentionally creates monthly customer records containing demographics, contractual attributes, service characteristics, usage, complaints, recharges, and short complaint texts. The churn label is generated in the same program from a transparent probability rule: month-to-month contracts, short tenure, and low average monthly revenue increase the base probability. The code then aggregates each customer's monthly history, fits candidate classifiers, and exposes a prediction service to a browser dashboard.

This design creates a useful educational and engineering artifact, but it also changes the research claim that is appropriate. The objective is not to establish a deployable telecom model or to report superiority over published systems. It is to document a reproducible prototype that compares three implemented classifiers, makes its data-generating assumptions explicit, and connects a selected model to a user interface and retention workflow. The main contributions are:

1. A reproducible, six-month synthetic customer panel and customer-level feature construction procedure implemented in Python.
2. An implemented comparison of Logistic Regression, Random Forest, and XGBoost under one stratified hold-out protocol.
3. A Flask/React integration that returns churn probabilities, SHAP-based explanations when available, and risk/CLV-based retention suggestions.
4. A transparent account of limitations that would need correction before the prototype is evaluated on real telecommunications data.

## II. Related Work

Churn modelling has long been studied as a customer-relationship-management problem. Neslin *et al.* evaluated the predictive accuracy of churn models using wireless-carrier data and highlighted the importance of modelling choices and target definition [2]. Verbeke *et al.* further argued that conventional statistical measures alone may not select the most profitable campaign target set, proposing a profit-driven perspective for the telecom sector [1]. These studies motivate the project’s use of probability estimates and its downstream retention layer, although the current code does not perform profit optimisation.

The classifier choices represent common complementary approaches. Logistic Regression estimates the log-odds of churn as a linear combination of predictors and is readily interpretable. Random Forest aggregates randomized decision trees to reduce variance [3]. Gradient-boosted trees build an additive model by sequentially minimizing a loss function [4], while XGBoost provides an efficient regularized tree-boosting implementation [5]. These techniques are included as separate candidates in the repository; no voting ensemble is implemented.

Churn data can be imbalanced, so a high accuracy alone may obscure weak detection of the attrition class. Burez and Van den Poel discuss the problem specifically for customer churn [6]. Accordingly, this study reports precision, recall, F1-score, and ROC–AUC in addition to accuracy. ROC analysis is useful for comparing the ranking capability of probability models across thresholds [7].

The project also contains a SHAP explainability module. SHAP assigns feature attributions to a particular prediction and provides a unified framework for additive feature attribution [8]. In this implementation, a `TreeExplainer` is used for models with `feature_importances_`, while `shap.Explainer` is otherwise used. The existing SHAP summary image gives a global view of the fitted model's feature effects. The research gap addressed here is therefore practical rather than algorithmic: a small, reproducible pipeline links synthetic longitudinal records, conventional classifier comparison, explanation code, and a retention-facing interface. It does not claim a new learning algorithm.

## III. Dataset and Problem Formulation

### A. Synthetic data source and composition

The only dataset source in the project is `create_sample_data` in `backend/main.py`; no CSV, database, or external data URL is present. With its main-program arguments, the function uses NumPy seed 42 and creates 1,000 customer identifiers over months 0–5, producing 6,000 monthly rows. The verified run contains 3,906 non-churn monthly rows and 2,094 churn monthly rows. Since the label is constant for all six records of a customer, the customer-level modelling dataset has 651 non-churn customers and 349 churn customers.

At the monthly level, the raw variables are `customer_id`, `month`, `age`, `tenure`, `avg_monthly_revenue`, `contract_type`, `internet_service`, `phone_service`, `data_usage`, `complaints`, `recharges`, `complaint_text`, and `churn`. Contract type takes month-to-month, one-year, or two-year values; internet service takes DSL, fiber optic, or no service. The project defines churn as a generated binary response, not as a documented service-termination event from an operator. Consequently, its numerical results quantify recovery of the program's simulated pattern and must not be interpreted as a real-world churn rate.

### B. Customer-level prediction task

Let each aggregated customer record be represented by a feature vector $\mathbf{x}_i\in\mathbb{R}^{d}$ and its generated label by $y_i\in\{0,1\}$, where 1 denotes churn. A classifier estimates

$$p_i=P(y_i=1\mid\mathbf{x}_i).$$

For a threshold $\tau$, the predicted label is $\hat{y}_i=1$ when $p_i\geq\tau$ and 0 otherwise. The training code uses each estimator’s default classification threshold for class predictions and uses $p_i$ for ROC–AUC. The selected model is the model that maximizes hold-out ROC–AUC, not accuracy or F1-score.

## IV. Proposed Methodology

### A. Feature construction and aggregation

The pipeline first orders records by `customer_id` and `month`. It computes a rolling three-month mean and standard deviation of data usage, the one-month difference in usage (`usage_trend`), cumulative complaints, complaint change (`complaints_increase`), rolling recharge frequency, and recharge change (`recharge_trend`). Missing values introduced by rolling calculations are back-filled, forward-filled, and finally replaced with zero. CLV is calculated as

$$\mathrm{CLV}=\mathrm{avg\_monthly\_revenue}\times\mathrm{tenure}.$$

The feature engineer attempts sentiment analysis on `complaint_text` using `nlptown/bert-base-multilingual-uncased-sentiment`. During the verified execution, the transformer model was unavailable and all `sentiment_score` values were set to the implemented neutral fallback, 0.5. The manuscript therefore does not treat sentiment as an empirically learned signal in this run.

For modelling, the latest monthly record is merged with per-customer aggregate statistics: mean, standard deviation, minimum, and maximum data usage; total and mean complaints; total and mean recharges; and number of monthly records. The feature-selection list retains 19 predictors: 16 numeric or Boolean-valued predictors and the two categorical fields `contract_type` and `internet_service` (the Boolean `phone_service` is identified as numeric). Together with the label, the customer-level dataframe has 20 columns. Following one-hot encoding, the processed matrix has 22 columns.

### B. Preprocessing and split

`DataPreprocessor` identifies object/category columns as categorical and numerical dtypes as numeric. It applies median imputation and `StandardScaler` to numeric columns. It applies most-frequent imputation and `OneHotEncoder(handle_unknown='ignore', sparse_output=False)` to categorical columns. The 1,000-by-22 processed matrix is then divided with `train_test_split(test_size=0.2, random_state=42, stratify=y)`, yielding 800 training and 200 test customers.

The order matters: the repository fits the preprocessor to the whole customer-level feature matrix before the hold-out split. This is a form of preprocessing leakage because imputation, scaling, and categorical vocabulary have access to test-set covariates. It is reported here as an implementation fact, not endorsed as best practice. A production-quality evaluation should split raw customer records first and fit all learned preprocessing steps only on training data.

### C. Models and selection

The `ModelTrainer` initializes the following models with `random_state=42`:

| Model | Implemented configuration |
|---|---|
| Logistic Regression | `max_iter=1000` |
| Random Forest | `n_estimators=100` |
| XGBoost | `eval_metric='logloss'`; other library defaults |

No hyperparameter search, resampling method, threshold optimization, calibration step, or ensemble voting appears in the training code. For each classifier, the system calculates accuracy, positive-class precision, recall, F1-score, and ROC–AUC. The model with the maximum ROC–AUC is retained and may be serialized through `joblib`.

### D. Explanation and retention process

For the selected model, the explainability component returns local SHAP-based feature contributions and may render a global SHAP summary plot. The existing plot ranks `data_usage_mean` visually as the most spread feature contribution, followed by complaint and data-usage aggregate variables. This is descriptive of the checked-in plot; no numerical mean-absolute-SHAP table is emitted by the code.

`RetentionEngine` assigns High risk for probabilities at least 0.7, Medium for probabilities from 0.4 to less than 0.7, and Low otherwise. It marks CLV at least 1,000 as High value. A risk/value lookup selects a recommendation such as a premium retention package or monitoring. The API also computes an illustrative potential-revenue value as `monthlyCharges × 24` and multiplies it by risk and an assumed success rate. These are dashboard heuristics, not measured savings or causal treatment effects.

## V. System Architecture and Implementation

The system has three executable layers:

```text
Synthetic monthly generator (Python)
        ↓
FeatureEngineer → customer-level aggregation → DataPreprocessor
        ↓
Logistic Regression / Random Forest / XGBoost evaluation
        ↓
Best-by-ROC–AUC model + SHAP explanation + RetentionEngine
        ↓
Flask REST API (/api/predict, /api/retention-advice, /api/run-pipeline)
        ↓
React 19 + Vite dashboard
```

The Python requirements name pandas, NumPy, scikit-learn, XGBoost, Transformers, PyTorch, SHAP, Matplotlib, Seaborn, Flask, and Flask-CORS. The web client is implemented with React 19.2 and Vite 7.3. The API initializes a smaller 100-customer, six-month synthetic dataset when it starts; this API training mode is distinct from the 1,000-customer main-program experiment reported in Section VI. Incoming dashboard payloads are mapped into the preprocessor schema, with unavailable fields filled by neutral defaults. The `/api/predict` endpoint returns a probability and High/Low label at a 0.5 threshold; `/api/retention-advice` applies the risk/CLV heuristics.

This is plausible because the label generator itself uses a small set of additive rule effects. It is not evidence that Logistic Regression would generally outperform tree models on actual telecom data; tree methods may benefit when real interaction effects and non-linearities are present.

The choice of threshold should therefore be determined from real campaign cost, intervention capacity, and expected retention benefit; the project does not contain this analysis.

## VII. Discussion

The project demonstrates how an estimated churn probability can be connected to an operational screen. A telecom analyst could prioritize high-probability customers, inspect the available explanation, and select a suitable retention communication. The dashboard’s use of CLV produces a simple prioritization mechanism: high-risk/high-CLV customers receive an intensive retention recommendation, whereas low-risk/low-CLV customers receive no immediate action. This structure is readily understandable for demonstration purposes.

However, the recommendation mechanism should be distinguished from a validated retention policy. The code uses thresholds of 0.7 and 0.4, a CLV threshold of 1,000, a fixed 24-month horizon, and assumed retention success rates of 0.7 or 0.8. None is learned from campaign data. These settings can support interface prototyping but cannot establish expected savings. In a deployment study, the organization would need observed campaign outcomes, offer costs, contact constraints, and an experimental or causal design to measure incremental retention.

The results also show a practical trade-off. XGBoost recovers two additional churners relative to Logistic Regression (43 versus 41) but generates eight additional false positives (21 versus 13), and it has lower ROC–AUC. The correct selection depends on whether missing a churner or contacting a stable customer is costlier. Selecting Logistic Regression by ROC–AUC is consistent with the implemented code, but it is not a universal decision rule.

## VIII. Limitations

The principal limitation is synthetic-data circularity. Churn is produced from a known simplified rule involving contract type, tenure, and average monthly revenue, and the model is evaluated on records generated by that same program. The results do not provide external validity, establish causal drivers, or demonstrate performance on an operator's changing population.

Second, preprocessing is fitted before splitting, which permits hold-out covariate information to influence transformations. Third, the feature engineer’s attempted sentiment model did not load in the verified environment; the neutral fallback means no sentiment signal was actually extracted. Fourth, a single random split is reported without confidence intervals or temporal validation. Fifth, the API trains a smaller fresh synthetic dataset at start-up rather than loading the checked-in serialized model, so dashboard scores need not equal the main-program scores. Finally, some dashboard inputs do not have corresponding training features and are substituted with default values; this limits the fidelity of individual API predictions.

## IX. Conclusion and Future Work

This paper documents a working full-stack telecom churn prototype that generates a six-month synthetic panel, aggregates customer features, compares three classifiers, and surfaces predictions through a Flask/React interface. In the verified 1,000-customer experiment, Logistic Regression was selected by ROC–AUC (0.8329), with accuracy 0.7900 and F1-score 0.6613. The existing SHAP module and risk/CLV recommendations make the prototype more inspectable than a prediction-only demonstration.

The next credible step is not to claim higher performance but to replace the synthetic generator with a governed real dataset, define churn and intervention outcomes with the provider, split data temporally before preprocessing, and evaluate using repeated or time-based validation. Future work should fit preprocessing and feature engineering on training data only, calibrate probability thresholds to observed campaign economics, persist one verified pipeline for the API, add ROC and confusion-matrix artifacts, and validate whether explanation-informed offers improve retention. Only after those steps would deployment-scale claims be justified.
